## Джерело

та `GET /api/v1/accounts/:id/statuses`. Для публічних хештегів авторизація не потрібна,
тому немає ризику блокування особистого акаунта. Цілі збору: `tag:osint, tag:ukraine, tag:infosec, tag:osint@infosec.exchange`.

## Які ліміти зустріли
- Сервер у кожній відповіді повертає `X-RateLimit-Limit / Remaining / Reset`.
  Виміряно: **Limit = 300**, мінімальний Remaining за весь збір = **285**.
  (За документацією Mastodon це ~300 запитів на 5 хв з однієї IP / одного токена.)
- Сторінка — максимум **40** записів (`limit=40`), більше API не віддає.
- Усього запитів: **24**, відповідей **429: 0**, 5xx: 0, мережевих збоїв: 0.
  Значення Retry-After, які приходили: не приходили. Жодного 429 не отримали: пейсинг тримає темп нижче ліміту, а гілку обробки 429/Retry-After перевірено офлайн-тестом `test_429_respects_retry_after` (фейковий сервер віддає 429). Середній час відповіді: 742 мс.
- Значення `X-RateLimit-Reset` (UTC): 19:30:00, 19:25:00, 19:20:00, 19:15:00 — вікно ліміту скидається на межі кожних 5 хвилин.
- Збої, що трапились під час збору (ціль ізольовано, решта прогону продовжилась):
  - `tag:osint@infosec.exchange` — 3 прогін(и): `FatalHTTPError: HTTP 422 for https://infosec.exchange/api/v1/timelines/tag/osint?limit=40: {"error":"This method requires an authenticated user"}`
- Деякі інстанси (напр. `infosec.exchange`) вимикають анонімний перегляд стрічок: API відповідає
  **422 «This method requires an authenticated user»**. Це не тимчасова помилка, тому колектор не повторює
  запит (не марнує ліміт), а фіксує збій у `runs`. Рішення — додати токен цього інстансу в `MASTODON_TOKENS`.

## Як обходили (поважали) ліміти
1. **Пейсинг:** пауза ≥ 1.5 с між запитами до одного хоста → максимум ~200 запитів за 5 хв, тобто з запасом нижче ліміту.
2. **Адаптивне гальмування:** коли `Remaining ≤ 10`, колектор сам чекає до `X-RateLimit-Reset`, не доводячи до 429.
3. **429:** чекаємо `Retry-After` (або `X-RateLimit-Reset`), якщо їх нема — експоненційний backoff `2.0^n` + jitter, максимум 5 повторів.
4. **5xx / таймаути / обриви мережі:** повтор з backoff; якщо ціль так і не відповіла — вона позначається `error` у таблиці `runs`, а інші цілі збираються далі.
5. **Невеликі партії:** 3 сторінки на ціль за прогін; курсор зсувається лише після запису сторінки в БД.
6. **Ротація** (бонус): кілька токенів (`MASTODON_TOKENS`) × проксі (`PROXIES`); ідентичність, яка отримала 429, іде на cooldown, запит робить наступна.

## Інкрементність і dedup
- `forward`: `min_id = останній зібраний id` → лише нові пости; повторний запуск продовжує з того ж місця.
- `backfill`: `max_id = найстаріший зібраний id` → одноразовий добір історії до кінця (`backfill_done = 1`).
- Унікальність: `uid` (PRIMARY KEY) і `url` (UNIQUE) + `INSERT OR IGNORE` → той самий пост під двома
  хештегами або при повторному прогоні не дублюється; прогін ідемпотентний.
